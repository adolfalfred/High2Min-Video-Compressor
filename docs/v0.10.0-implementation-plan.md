# High2Min Video Compressor 0.10.0 implementation plan

## Scope

Version 0.10.0 will add flexible number-based video ordering and a verified in-app update downloader. The existing compression, ADT transaction, hand-sign control, simultaneous voice-over/video playback, and ZIP-preservation guarantees must remain unchanged.

## 1. Number-based video discovery and ordering

### Required behavior

- Accept an MP4 when its filename stem contains one unambiguous positive integer, regardless of the surrounding words.
- Treat that integer as the ADT page number and sort videos numerically rather than alphabetically.
- Accept leading zeroes while normalizing the value: `003` maps to page 3.
- Continue writing normalized ADT destinations and mappings as `page_3.mp4` and `video-3`.
- Show the original source filename, inferred page number, and normalized destination in progress, validation errors, reports, and a pre-publish mapping preview.
- Reject page 0, numbers beyond the website page count, duplicate inferred page numbers, files with no number, and filenames containing multiple ambiguous number groups.
- Never guess when a filename could map to more than one page.

### Examples

| Source filename | Inferred page | Result |
| --- | ---: | --- |
| `1.mp4` | 1 | `page_1.mp4` |
| `sign language 12.mp4` | 12 | `page_12.mp4` |
| `lesson-003-final.mp4` | 3 | `page_3.mp4` |
| `unit2-page10.mp4` | — | Rejected as ambiguous |
| `introduction.mp4` | — | Rejected because it has no number |

### Implementation

1. Replace `PAGE_VIDEO_PATTERN` with an isolated filename-to-page parser.
2. Keep discovery case-insensitive for the `.mp4` extension.
3. Validate every inferred page before any repository change.
4. Sort `PageVideo` objects by inferred page number.
5. Add mapping data to CLI JSON and desktop preview/status output.
6. Add tests for spaces, punctuation, Unicode words, leading zeroes, numeric sorting, duplicate pages, ambiguous names, zero, and out-of-range pages.

## 2. Automatic startup update checks

### Required behavior

- Start a background update check every time the desktop app opens, whether or not a manual update button exists.
- Keep app startup and normal work available while the network request runs.
- Keep automatic offline failures silent but record them in diagnostics.
- Preserve an optional manual check action without making the automatic service depend on its widget.
- Cache the last release metadata and HTTP validators such as `ETag`; startup still checks, while unchanged releases use a lightweight conditional request.

### Architecture

- `UpdateCoordinator`: owns startup checks and download state independently of Tk widgets.
- `GitHubReleaseClient`: fetches stable release metadata with strict response limits and timeouts.
- `PlatformResolver`: maps the current OS and processor to exactly one release target.
- `UpdateDownloadManager`: streams the selected archive to a temporary `.part` file.
- `IntegrityVerifier`: checks the downloaded archive against its matching SHA-256 sidecar and expected release metadata.
- Desktop UI: displays update availability, download progress, cancellation, completion, and errors.

## 3. In-app platform download

### Platform mapping

| Runtime | Release target |
| --- | --- |
| Windows AMD64/x86-64 | `windows-x86_64` |
| Linux AMD64/x86-64 | `linux-x86_64` |
| macOS arm64/Apple Silicon | `macos-arm64` |
| macOS Intel x86-64 | `macos-x86_64` |

Unsupported processors must receive a clear message and no guessed download.

### Safe download flow

1. Detect a newer stable, non-draft, non-prerelease version.
2. Select one exact archive and its exact `.sha256` asset for the current platform.
3. Ask the user to confirm the version, platform, size, and destination.
4. Download inside the application with byte progress and cancellation.
5. Allow only trusted GitHub release/API hosts and enforce response and archive size limits.
6. Write to a unique `.part` file, flush it, calculate SHA-256, and compare it with the verified sidecar.
7. Delete partial or mismatched files and leave the installed application unchanged.
8. Atomically rename a verified download to its final archive name.
9. Offer **Open download folder** and platform-specific installation instructions.

The first 0.10.0 implementation will download and verify the correct archive but will not silently execute it or replace the running application. Windows and macOS releases are currently unsigned, and the distributed format is a portable archive rather than a signed installer. Fully automatic installation should be revisited after signed installers and a dedicated updater helper are available.

## 4. Reliability and security tests

- Filename parsing, ambiguity, duplicates, range validation, and numeric ordering.
- Windows, Linux, macOS arm64, macOS x86-64, and unsupported-platform resolution.
- Newer/current/older, draft, prerelease, malformed, oversized, and untrusted release responses.
- Correct archive selection when release assets arrive in any order.
- Streaming progress, cancellation, connection loss, truncated downloads, disk errors, checksum mismatch, and cleanup.
- Startup check behavior with no manual update widget.
- UI responsiveness during check and download.
- Native GitHub Actions tests and frozen-archive smoke tests on all four release targets.

## Acceptance criteria

- Videos with one clear number are ordered and published correctly without requiring the word `page`.
- Ambiguous and duplicate mappings stop before repository changes and explain how to correct them.
- Every desktop launch checks for updates in the background independently of UI button placement.
- Users can download the correct platform archive inside High2Min with visible progress and cancellation.
- Only a SHA-256-verified complete archive becomes visible as a finished download.
- The running application is never overwritten or executed automatically.
- Existing compression, ADT rollback/recovery, accessibility controls, and ZIP-preservation tests remain green.
